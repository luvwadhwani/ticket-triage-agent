# Ticket Triage Agent: design spec

Date: 2026-10-06 · Owner: Luv Wadhwani · Status: draft for review

## 1. Why this exists

A public, clickable portfolio piece for Luv's Upwork profile ("AI Agent Architect & Fractional
Engineering Lead"). It has to prove one thing to a client in under two minutes: **Luv ships AI
agents that do real work safely**: tool use, visible reasoning steps, and hard guardrails that keep
a human in charge of risky actions.

Constraints agreed in brainstorming:

- Built on Luv's own time and accounts; public repo; nothing from any employer or client (no code,
  data, names, screens). The domain is customer support for a **fictional** SaaS company, "Acme Cloud".
- Cheap to run: a few dollars a month.
- Visitors cannot type their own tickets. They choose from 8 preset tickets (keeps cost bounded and
  removes prompt-injection risk from the public surface).

Success looks like:

1. A deployed URL where any of the 8 tickets plays back a real recorded agent run, and "Run it live"
   re-runs it for real within rate limits.
2. Safety rules hold 100% on the eval set; triage accuracy is measured and published honestly.
3. A README that reads as a case study, and an Upwork portfolio item linking to the demo and repo.

## 2. What a visitor sees (approved layout A: three-pane console)

Header: "Ticket triage agent: demo · Acme Cloud (fictional)", a **Recorded run / Run it live**
control, a GitHub link and a "How accurate is it?" link.

| Inbox (left) | Agent run (middle) | Your decision (right) |
|---|---|---|
| 8 preset tickets: subject, sender, plan | Live step timeline: each tool call with its input and a one-line result, plus the classification chips (category, priority, confidence) | The draft reply (citing the help article it used), a "Why it stopped" banner naming the rule that fired, and **Approve & send / Edit / Escalate** |

- Buttons are demo-only. Nothing is ever sent. Approve shows "Would send this reply to
  maya@example.com"; Escalate shows "Handed to Billing team with this note…".
- Recorded runs are labelled "Recorded run from <date>". Live runs are labelled "Live run".
- Desktop-first; on narrow screens the panes stack and the inbox becomes a dropdown.

Prototype of the approved layout: `docs/superpowers/prototypes/console-layouts.html` (option A).

## 4. Architecture

One Next.js (App Router, TypeScript, Tailwind) app on Vercel. Agent loop on the Vercel AI SDK
(v7; verify APIs against `node_modules/ai/docs` when building), model **Claude Sonnet** through
the **Vercel AI Gateway** (exact gateway model string verified at build time). No database.

```
app/
  page.tsx                  three-pane console
  evals/page.tsx            "How accurate is it?" (renders evals/results.json)
  api/run/route.ts          POST {ticketId} → streams a live run (preset IDs only)
components/
  Inbox.tsx  RunTimeline.tsx  DecisionPanel.tsx  RunModeToggle.tsx
lib/
  agent/run.ts              the tool loop, system prompt, 8-step cap; emits RunEvent[]
  agent/events.ts           RunEvent types shared by live and recorded runs
  tools/                    one file per tool (below), each a pure function over data/
  policy.ts                 safety rules, applied AFTER the agent finishes
  replay.ts                 plays a recorded run with its original timing (sped up, capped)
data/
  customers.json  invoices.json  status.json  docs/*.md (~20 help articles)
  tickets.json (8 presets)
runs/<ticketId>.json        recorded runs, generated by scripts/record-runs.ts and committed
evals/cases.json            ~25 labelled tickets; evals/results.json + results.md (generated)
scripts/record-runs.ts  scripts/run-evals.ts
```

### Tools (all read fake data from `data/`, no real systems)

| Tool | Returns |
|---|---|
| `classify_ticket` | the model must call this first; its validated arguments *are* the classification: category, priority, confidence 0–1, intents (refund, cancel, security, incident…) |
| `lookup_customer` | plan, status, signup date |
| `get_invoices` | recent invoices; duplicate charges are visible in the data |
| `get_service_status` | per-component status (API, dashboard, billing) |
| `search_docs` | top 3 help articles by keyword score, with ids for citation |
| `draft_reply` | reply text plus the doc ids it cites |
| `escalate` | team + reason (Billing, Engineering, Security, Success) |

### Safety rules (`lib/policy.ts`, enforced in code)

Evaluated on three inputs: the classification, the tool results (e.g. a duplicate charge in the
invoices), and a deterministic keyword check on the ticket text (refund, chargeback, cancel, delete
my account, password, SSO, 2FA, down, outage…). A wrong classification alone therefore cannot skip a
rule. Rules run after the agent and can only make the outcome more cautious.

| Rule | Trigger | Outcome |
|---|---|---|
| Refund | intent refund/credit/charge reversal, or a duplicate charge found | Needs human |
| Account deletion | intent cancel/delete account | Needs human |
| Security | intent login/SSO/2FA/password/suspicious access | Needs human |
| Low confidence | confidence < 0.70 | Needs human |
| Incident | status check shows an outage, or intent incident | Escalate to Engineering, Urgent |
| Couldn't finish | 8-step cap hit, or a tool still failing after one retry | Escalate with reason |

Final outcome is one of: **Ready to send**, **Needs human (rule)**, **Escalated (team)**.

## 5. Cost control

- **Recorded runs:** `scripts/record-runs.ts` runs the real agent once per preset ticket and saves
  the event stream to `runs/`. The page replays these by default: zero API cost per visit.
- **Live runs:** `POST /api/run` accepts preset ticket IDs only. Protected by a Vercel Firewall
  rate-limit rule (about 5 live runs per IP per day) and an AI Gateway monthly budget cap
  (proposed **$10**, set by Luv). Expected cost per live run: about $0.05–0.10.

## 6. Error handling

- Tool error → structured error back to the model; one retry; then the "couldn't finish" rule escalates.
- Live run unavailable (rate limit, budget cap, gateway error) → the UI says so and falls back to the
  recorded run for that ticket. A visitor never sees a broken page.
- 8-step cap on the loop.
- Policy layer always has the final say over the model's proposed outcome.

## 7. Testing and evaluation

- **Unit tests (Vitest):** every tool; every safety rule as a table test proving it forces the
  cautious outcome; the replay timing logic.
- **Evals (`npm run eval`, run manually, costs a few cents):** ~25 labelled tickets, including vague
  ones and injection attempts. It reports category accuracy, priority accuracy, and escalation
  precision/recall, written to `evals/results.json` and `results.md`. **Safety rules must score
  100%**; any miss fails the run. Accuracy is published as measured; the target is ≥ 85% category
  accuracy, but the number shown is the real one.
- **Browser test (Playwright):** load page → pick ticket 1 → recorded run plays all steps →
  "Why it stopped: refund rule" shows → Approve → "Would send…" state. It runs locally and against
  the Vercel preview URL. Before calling it done, the deployed page is also driven by hand and
  screenshotted.
- **CI (GitHub Actions):** lint, typecheck, unit tests and the Playwright test against a production
  build. Evals are not in CI (they cost money).

## 8. README and Upwork item

README sections: what it does (with a GIF), architecture diagram, the safety rules table, eval
results, cost per run, how to run locally, and what is deliberately out of scope. It doubles as the
case study.

Upwork portfolio item: a screenshot of the console as the cover, title and description in the
house style used for the first two items, a live demo link and a repo link, and skills (AI Agent
Development, Large Language Model, TypeScript, React, Agentic Workflows).

## 9. Out of scope

Free-text tickets from visitors; real email or helpdesk integrations; vector database or
embeddings; user accounts or auth; multiple tenants; any real company's data or naming.
